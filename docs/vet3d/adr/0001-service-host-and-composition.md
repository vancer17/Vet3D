## 背景

Vet3D 的目标是供 BFF 调用的后端服务，后续承担自主执行、验收、预算内修订及明确终态。仓库既有 Python 工具用于 Hi3D 参考盘点和归档，其存在不能作为产品运行时已经建立或产品技术栈已经选定的依据。

L0-01 需要尽早建立可运行的应用入口和测试装配，验证稳定业务代码与可替换依赖的关系。此时身份、文件引用、完整状态和真实模型端口尚未实施，首项不应依赖后续条目的完整实现。

## 决定

1. 使用独立 CPython 3.14 环境，以 uv 管理环境和依赖，以 Hatchling 构建 src-layout 项目。当前 Debian 是本项验证平台，系统其他 Python 版本不作为静默回退。
2. 使用具体应用服务和消费者拥有的小型依赖端口。正常骨架明确装配演示适配器，测试直接注入机械替身，不增加 Mock 模式业务配置。
3. Bootstrap 拥有装配、调用生命周期和日志初始化；CLI 仅是非交互验收入口。本项不引入 HTTP，跨进程 BFF 集成由其实际接口与消费者确定后单独接入。
4. 跨包只通过各自公共导出访问；应用模块不导入具体适配器或 Bootstrap。根包不导入既有 Hi3D 工具，产品构建显式隔离参考代码和原件。
5. 当前演示契约局限于装配验证。共享类型只在存在实际消费者与稳定语义时提升；不提前创建全局状态、作业账本或模型动作集合。

当前参数、回复、超时、取消、CLI 和日志行为只在 [L0-01 实施卡](../implementation/work-items/L0-01.md)维护，本 ADR 不复制其接口定义。

## 评估过的替代方案

| 替代方案 | 本次未采用的原因 |
| --- | --- |
| 将 CLI 确立为产品交互中心 | 产品目标是 BFF 调用的后端；CLI 适合验收装配，但不应决定产品交互或要求持续人工确认。 |
| 首项直接增加 HTTP 服务及完整 Web 框架 | 当前检查的是应用边界与依赖替换，尚无真实 BFF 消费协议；提前引入传输和服务器生命周期会扩大本项验收。之后真实接入仍必须单独验证。 |
| 基于现有 Python 归档工具直接延伸产品 Runtime | 参考工具的职责、输入输出和证据边界不同；产品应用保持独立模块和构建范围。 |
| 预先创建统一 `contracts`／`kernel` 及所有未来端口 | 容易把供应商类型、业务状态和宿主事实混入共享层，并产生无消费者的接口。当前依赖端口由消费者拥有，后续按实际复用提取稳定语义。 |
| 为稳定应用服务再定义镜像 Protocol 或服务定位器 | 当前稳定服务没有需要替换的同类实现；重复包装及动态查找会隐藏依赖。真正可替换的依赖使用一个明确端口。 |
| 在业务 Settings 中选择 Mock、运行架构或兼容分支 | 测试装配可以直接注入，不需要产品模式开关；兼容仅在真实消费者或持久数据需要时另行决策并规定退出条件。 |
| 自动使用系统 Python 或同时承诺多个平台 | 不能保证环境一致，也无法由当前 Debian 的一次验证推导跨平台支持；按已批准环境实施并记录实际版本。 |

## 后果与后续边界

异步入口为后续外部服务和执行器留下调用边界，但其机制测试不证明模型语义、质量或长任务恢复。真实 Agent SDK、LLM、模型供应商、数据库与传输适配的接入仍依对应分层条目验收。

模块依赖可以在最小范围内验证。日志由 Bootstrap 集中配置，业务模块不用部署 Settings 改写动作协议；具体运维能力随真实部署需求接入。本项不对未来端口、产品 API 或状态枚举提供提前兼容承诺。

构建与日志的集中管理要求对应测试同时覆盖正常执行和必要失败边界。测试替身验证机械行为；需要真实 LLM 理解或生成能力的结论，必须使用真实模型另验。
