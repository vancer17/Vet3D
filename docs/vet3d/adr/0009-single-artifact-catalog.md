# ADR 0009：单资产目录与独立文件 I/O

| 字段 | 内容 |
| --- | --- |
| 状态 | 已接受并实施；当前契约及实际验收由 [L1-04](../implementation/work-items/L1-04.md)维护。 |
| 日期 | 2026-11-24。 |
| 范围 | 已保存资产的单件持久登记、真实 ArtifactAccess 及所必需的并行边界。 |

## 背景

L1-01 已有持久工作区，L1-02 已能保存及观察实际文件，L0-05 的生成服务已经逐项解析登记和核对文件。实际缺口是重启后仍能取得原资产元数据，并把真实目录接入这个消费者。既有文件操作复用单控制线程，使大文件复制期间同根元数据查询也报忙，无法支持不同工作区独立推进。

最初候选设计包括多文件原子可见、批次意图、成员提前绑定、批内派生图和未完成批次重启恢复。复核当前消费者后，这些结构没有必要：生成服务在领取尝试之前已经检查全部输入，部分目录登记不会被视为完整生成输入。用户明确要求减少没有当前消费者的状态空间和兼容成本。

## 决定与理由

1. **以单个不可变资产为提交单位。** 复用已有身份、内容及位置记录，SQL 行存在就是登记事实。文件落盘与元数据提交分开，已提交字段精确重放只读回，不增加状态镜像、批次主键或资产意图。
2. **只为实际消费建立端口。** ArtifactRepository 承担元数据持久边界，真实文件继续由已有 ArtifactFileStore 提供；Bootstrap 组合为原 ArtifactAccess。没有通用 Unit of Work、事件总线或独立报告仓储。
3. **按部署资源分离控制与文件 I/O。** SQLite Session 和根生命周期保持唯一控制线程，文件操作在有限线程中持有独立描述符。保留根所有者互斥，不将其扩展为所有建模操作串行。并行配额只控制宿主资源，不定义业务能力。
4. **可变工作文件留给执行环境。** 只有冻结候选进入不可覆盖的接收与登记；普通保存和临时截图不必建立目录记录。后续模型版本及候选提交由真实业务消费者定义，当前不创建“当前版本”指针。
5. **兼容性由真实存量驱动。** 当前可见仓库及配置没有保留产品库，因此以唯一 SQLAlchemy metadata 初始化和严格重开；旧结构明确拒绝并保留。若以后发现真实存量，单独设计迁移，不能删除数据或引入运行时新旧架构开关。

## 未采用的扩展

| 候选 | 未采用原因与未来触发 |
| --- | --- |
| 全批次原子可见和恢复协议 | 当前输入守卫不依赖目录级批次可见性；只有未来真实消费者需要不可拆分集合提交时再评估。 |
| 成员预留、批内派生 DAG | 目前没有持久化该类关系的消费者；执行与派生应沿已有身份模型在相应条目接入。 |
| 报告声明独立仓储 | 当前只需处理报告字节；评审、模型验收与发布的事实所有者尚未接入。 |
| 整个文件复制期间占用控制入口 | 不必要地阻断跨工作区元数据与其他文件；目录根所有权不要求文件字节串行。 |
| 资产登记兼作 Blender 日常保存 | 将可变编辑与不可变候选混为一体，增加无效身份和恢复工作。 |
| 迁移框架、双 Schema 运行与兼容投影 | 没有已存在消费者或持久数据依据；这类兼容必须单独记录实际数据及移除条件。 |
| 扫描文件自动认领或自动清理 | 文件存在不能证明身份及提交意图，可能将未知结果伪装成已登记或误删候选。 |

## 依据与后果

Hi3D 的[文件登记机制](../../hi3d/infrastructure/workspace/register-file-artifact.md)是历史参考。Vet3D 的服务端持久性和并行策略须由当前实现与实测证明，不能从桌面行为推断。

SQLite 的[原子提交说明](https://sqlite.org/atomiccommit.html)针对数据库事务，不使外部文件复制成为同一事务；断电保证仍依赖操作系统及存储。SQLAlchemy 的 [SQLite 外键说明](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#foreign-key-support)要求逐连接启用外键；实现在进入显式事务前启用并回读设置，而不是只在表模型中声明。

缩小范围的结果是：重启可以读回已提交资产，不能恢复丢失的未提交输入、批次进度或执行任务。按原身份重读与重新观察由正常可信服务自动完成，无需持续人工审批。执行隔离、模型质量及业务发布保持各自的独立交接条件。
