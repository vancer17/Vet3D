# 游戏制作前的需求、素材与玩法约定

本页是制作前沟通的共用规则；各入口保留自己的问题重点和玩法边界。先读取本轮消息、已有附件、工程与已确认方案，只询问会改变本次结果的缺项。

## 1. 简短提问

新建游戏先用一轮 1–3 个简短问题明确：主题与风格、目标设备与输入方式、视角、玩家主要动作及目标（自由探索也可以没有胜负）。入口给出贴合主题的 2–3 个候选玩法和推荐理由，允许自由填写或明确委托 agent 决定；不要求用户先填完整策划表。不把示例玩法、地图数或角色动作自动视为用户选择。

在 desktop 中必须调用宿主 `user_interaction` 展示 option 面板，不能只在普通聊天里列问题。必要事实及玩法选择使用 `kind=input`，给出适用选项并允许自由填写；不设置默认答案或超时。非关键风格偏好使用 `kind=preference`，每题给出推荐项、推荐理由及对应 `defaultAnswer`，可设 `timeoutSeconds=60`；超时返回的 `source=assistant_default` 只能记为助手建议。其他宿主使用其等价交互工具。已有答案不重复问。文字面板只收文字，素材必须通过聊天附件或用户给定的可访问文件路径提供；没有附件入口时说明所需文件及用途，不假装面板能上传。

## 2. 索取与盘点素材

实际查看已有素材，再给简短清单：素材、用途、已有/缺失、必需/可选、缺失时的处理。按项目需要索取角色或卡图、场景与风格参考、GLB/FBX、Logo、音效或已有源码；不机械要求每个项目交齐全部类型。区分同一物体多视图与不同物体，区分风格参考与必须原样使用的素材。

没有素材不等于不能开始设计：向用户提供“上传素材”“文字描述后生成”“复用已有资产”的适用选择，记录实际来源。用户明确选择文字创作后才安排相应生成；用户要求等待素材时暂停依赖步骤，不用代理素材替代指定主体。必需素材未到时，可继续资料盘点与不依赖它的方案准备；方案尚未确定前不生成图片/模型、不编写游戏实现。

## 3. 展示可审阅的玩法方案

在包外任务目录写入 `hi3d-game-brief.md` 并向用户展示摘要：

- 主题、目标设备、视角与控制方式；已有工程的保留项。
- 一个核心闭环：进入 → 玩家动作 → 可见反馈 → 目标/胜负或自由探索 → 继续、返回或重开。
- 首版功能与暂不包含的内容，必要的场景、角色、卡牌和动作清单。
- 素材复用/上传/生成计划、必需缺项及可独立推进的部分；费用和发布范围只记录真实授权。
- 可观察的验收条件，以及待用户决定的关键取舍。

同时记录方案版本、用户实际选择或明确委托的来源、仍缺信息。未回答的关键项标为待定，不能把推荐值、偏好超时或沉默写成用户确认。不需要另建一套状态机；沿用入口检查点和宿主等待输入机制。缺少必要方案选择时保持首个检查点的 `waiting_choice`，按已有 `input_gap` 处理；`confirm_required` 仅保留给已有不可逆操作，不用于普通玩法选择。

## 4. 确定玩法后开始制作

展示方案后，通过宿主输入面板让用户选择“按此方案制作”“修改玩法”或“等待素材”。这是方案输入，不新增不可逆权限枚举；操作授权缺失时才使用确认面板。若用户已明确认可同一范围，或明确委托 agent 决定玩法并直接制作，记录依据、展示采用方案后继续，不重复询问。普通的一句主题或笼统“做一个游戏”不自动等于委托决定玩法。

新方案尚无认可/委托依据、必需信息未确定或用户要求等待时，停留在首个检查点；取消或拒绝后停止依赖步骤。必要输入不设置超时默认答案；可选偏好的默认值也不能替代玩法选择。面板失败时明确失败并用简短文字收集，不当作已经确认。收费生成、覆盖和发布遵从已有授权范围；认可玩法不自动扩大这些授权。

放行后才进入资产生成、场景搭建与游戏实现；需要用户素材的阶段还须等素材到齐。允许推进已确认方案中不受缺失素材影响的部分。阶段成果展示不变成反复审批，质量检查由执行者完成。

## 继续与局部修改

恢复原任务先复用已确认方案、素材和任务记录，从未完成步骤继续，不重新问整套问题或重复提交生成。修碰撞、改按钮、换一张卡等局部要求只补问影响该改动的缺项；用户明确的修改指令就是对应范围的依据，无需重新批准整个游戏。玩法、目标设备或必需素材发生实质变化时，只展示并确定受影响的方案差异，保留其余结果。
